02

Connect. Then check your identity.

A service URL, your own key, and the Claude companion plugin.

  1. Get the operator handoff.
    A working deployment, a training project, your individual companion key, and a permitted workflow.
  2. Load the connection securely.
    Claude needs VORNIK_URL and VORNIK_COMPANION_TOKEN in its environment. Use the credential issued for that endpoint.
  3. Install the companion plugin.
    Use the commands below with your local checkout path, then start a fresh Claude session that inherits the connection variables.
Inside Claude Code · replace the path
/plugin marketplace add /ABSOLUTE/PATH/TO/vornik
/plugin install vornik-companion@vornik
Ask Claude · verify before submitting
Use Vornik whoami with repo_scope="vornik-101-training", then catalog.
Tell me my project, effective scope, allowed workflows, and budget cap.
Do not display credentials or submit work yet.

Whoami = where you are. Catalog = what you can run.
Confirm the training project. A companion key does not automatically grant configuration administration.

Setup details and common connection mistakes

Keep token values out of chat and git. localhost works only when Claude and the daemon are on the same machine. Start with autonomy disabled. Use /help to confirm the installed plugin commands.

No deployment yet? Follow the installation guide. For exact operator and shell commands, see the optional connection lab.

Remember a decision. Recall it tomorrow.

Save useful facts

A decision with a date and context

Our fictional Team Cedar has a handoff rule. Store it once, then retrieve it in a fresh session.

Ask Claude · synthetic training data
Remember this decision under repo_scope="vornik-101-training":
"Team Cedar decided on 2026-10-08 that every weekly handoff requires one peer review before sharing."
Then recall the handoff rule and show its source and date.
Retrieve with context

Memory is evidence to review

Check the source, date, and relevance of a recalled fact. Use memory_correct when a claim becomes wrong or stale.

Specific scope: knowledge for one repository or training context.
* scope: cross-cutting knowledge within the project.

Scope is a retrieval filter.
Project and key permissions control access. A scope token is not an authorization boundary.

What RAG needs to work

Semantic recall needs a reachable embedding model and PostgreSQL/pgvector. Working chat alone does not prove embeddings work; check embedding readiness in whoami. Your key needs memory read/write permission, and new notes may take time to become searchable.

Strict recall drops legacy unscoped notes while still including *. See scope details.

04

Turn today's task into a repeatable routine.

Start with an available workflow. Keep the task small and the input explicit.

Supply context→Delegate→Keep working→Retrieve & review
Ask Claude · Team Cedar daily brief
Recall Team Cedar's handoff rule under repo_scope="vornik-101-training".
Include that decision in a delegation to companion-report-summarize using the same scope.

Inline notes:
Mira owns the onboarding checklist, due 2026-10-09.
Jon owns release notes, due 2026-10-12.
The demo environment is unavailable; owner and recovery date are unknown.
A customer demo next week is tentative; date and owner are unknown.

Request commitments, blockers, and uncertainties. Do not invent owners or dates.
Do not publish or send messages. Return the task ID immediately.

Later, ask Claude to call status, then result for that task ID. Read the artifact. Check that Mira and Jon keep their dates, the blocker stays visible, and the customer demo stays tentative.

Completed ≠ correct. Execution finishing is your cue to review the actual answer.

Create or adjust your own workflow

Have the operator copy a compatible shipped executable template under a new ID. Preserve its steps, role bindings, and output contract. Change the step prompt to your daily-brief format, save it in the daemon's actual configs tree, and authorize the new workflow for your key.

Operator commands · replace the config path
vornikctl workflow validate /ACTUAL/CONFIGS/workflows/daily-brief.md
vornikctl config reload
vornikctl config reload-status

Run it with the same input and compare the output. Validation checks the file; reload confirmation and a real run establish whether it works. Version the workflow file for teammates. Workflow reference.

Two delegation traps to avoid

A laptop path is not an upload. Supply inline text or attach the file's bytes; the agent cannot see your local filesystem.

A URL does not give a workflow browsing tools. Check network capabilities in catalog. Some companion workflows cannot browse.

05

Capture the procedure that worked.

A knowledge skill preserves how to do the job, after human review.

Search→Propose a draft→Human approval→Apply & verify
Ask Claude · make the procedure reusable
Search Vornik knowledge skills for a handoff review procedure.
If none fits, propose a project-scoped draft:
preserve known owners and dates, list unknowns explicitly,
and obtain one peer review before sharing a weekly handoff.
Show me the procedure for human review. Do not approve it.

Learners need skill read/write permission. An operator with skill_admin reviews and approves the draft. Use companion tools in Community Edition; the web admin inbox is an Enterprise convenience.

Approval makes a skill eligible; verify its use. Keep this procedure project-scoped. A global skill can reach roles across every project on the daemon.

“Skill” can mean three different things

Claude plugin skills: instructions for your local assistant.
Vornik knowledge skills: reusable procedures stored by the daemon.
Packaged SWARM-SKILL.md capabilities: bundles of workflow and role functionality.

Start with knowledge skills for team know-how. Knowledge skills reference.

The teammate handoff

  • The same appropriate team project and agreed scope.
  • An individual credential for each person.
  • A versioned workflow and the relevant skill.
  • Synthetic example input and expected output checks.

Your teammate should reproduce the brief without your original chat transcript.

Start manually

Run the routine yourself until its output is useful. Then consider scheduling with agreed triggers, costs, and review points.
